## Executive summary

The bounded discovery **orchestrator** (`runDiscovery`) is implemented and fully
tested offline: it selects a provider through the registry, drives discover →
(optional) fetch → normalize → identifier resolution → conservative dedup → a
candidate DECISION, enforces a hard budget, isolates per-item failures, retries
transient failures with bounded backoff, and persists reviewable candidates
through a persistence **port**. It writes nothing canonical, never publishes,
never classifies, and never calls AI.

**One STOP condition fired (as the M7.3 brief anticipated).** The real database
adapter that would write `import_candidate` rows **cannot enforce the required
candidate idempotency** — `(source_key, stable_source_id)` — on the current
schema. Per the M7.3 schema firewall (Phase 9, Phase 31, STOP conditions #1 and
#5), the migration was **NOT created**, idempotency was **NOT weakened**, and the
DB adapter was intentionally **NOT built**. The orchestrator instead writes
through a port with an in-memory adapter that enforces exactly the idempotency the
proposed DB unique index must, so the future adapter is a drop-in. The required
migration is proposed below for approval.

## Schema Firewall — the blocker and the proposed migration

**Inspected (actual repository, not assumed):**

- `import_candidate` (migration `0004`) columns: `id, import_job_id, raw_payload,
  normalized_payload, dedup_decision, duplicate_of_study_id, state, error_detail,
  created_at, updated_at`. **No `source_key` / `stable_source_id` column and no
  unique constraint** → candidate idempotency on `(source_key, stable_source_id)`
  is impossible to enforce in the database today.
- `import_job` (migration `0004`): `id, source_id→research_source, trigger, state,
  counts jsonb, started_at, ended_at, error_detail, …`. This **can** represent the
  run lifecycle as-is (state + counts + timestamps + error_detail). No change
  needed.
- RLS (`0008`, `0010`, `0012`): `import_job` / `import_candidate` have **staff-only
  SELECT** policies and **no INSERT/UPDATE** policies → writes must go through
  `service_role` (server-only), which bypasses RLS. This matches the M3 pattern.
- There is **no import data-access layer** in `packages/database` yet.

**Proposed migration `0013_discovery_candidate_identity.sql` (NOT created; awaiting
approval):**

```sql
-- Add the discovery candidate identity + enforce idempotency.
alter table import_candidate
  add column source_key       text,
  add column source_stable_id text;

-- Idempotency: one candidate per (source, stable source id). NULLs (manual/other
-- candidates) do not collide, so this is additive and safe for existing rows.
create unique index import_candidate_source_identity_uniq
  on import_candidate (source_key, source_stable_id);
```

- **RLS/grants:** no new policy is required for the write path — the server-side
  runner uses `service_role`, which bypasses RLS; the existing staff-only SELECT
  stays. (If a future non-service path is desired, a `with check
  (app.is_reviewer_or_admin())` INSERT policy would be added then, not now.)
- **Tests required with the migration:** PGlite tests that (1) a second insert of
  the same `(source_key, source_stable_id)` is rejected/idempotent, (2) NULL
  identity rows still insert freely, (3) anon/authenticated cannot INSERT, (4) the
  service-role path can.
- **Secondary (not blocking M7.3):** `research_source` has no natural unique key,
  so the future adapter should find-or-create a source by `(name)` /
  `(import_method, external_id)` rather than inserting per run (Phase 13). A unique
  index there would harden it but is not required for the candidate flow.

**Decision:** do not migrate without explicit approval. The orchestrator is
complete and the DB adapter is a thin, well-specified follow-up once `0013` is
approved.

## Discovery Orchestrator

`runDiscovery(request, deps)` — deps inject the registry, provider context
(injected fetch/contact/clock), the run + candidate stores, the study index, the
actor, and (for determinism) `now`/`sleep`/`rng`. Nothing is ambient.

## Provider Registry

Selection is registry-based only — there is no `if source === "crossref"`. The
orchestrator calls `registry.resolve(request.providerType, providerContext)`;
MOCK and CROSSREF resolve, PUBMED/EUROPE_PMC (and a fetch-less CROSSREF) fail
closed as `NOT_CONFIGURED`, recorded as a FAILED run.

## Run Lifecycle / Budgets / Pagination / Retries / Rate Limiting

Run: createRun (RUNNING) → paged processing → finalizeRun (COMPLETED/FAILED) with
counters + error summary. Budgets clamp every dimension to a hard maximum.
Pagination stops at `maxPages`, a null cursor, or a short page. Retries are
bounded per request and honour a Retry-After hint. The provider's
`SourceDescriptor` limits (rate/size/host) still apply inside each provider call.

## Normalization / Identifier Resolution / Deduplication / Idempotency

Normalization reuses the existing discovery boundary (`provider.normalize`); no
second system. The stable per-source id (canonical DOI for Crossref) is both the
provenance id and the idempotency key. Dedup is the conservative graded order via
the study-index port. Re-running the same run creates no duplicate candidates
(idempotency verified).

## Candidate Persistence / Provenance

Candidates persist through the port with: run id, source key, stable source id,
a minimised normalized payload (no full text), raw-payload hash, the dedup
decision (incl. related study id), and a candidate state
(`REVIEW_REQUIRED` / `DUPLICATE_CANDIDATE`). No canonical `research_study` /
`publication` row is ever written.

## RLS / Authorization / Security / AI Boundary / Canonical Boundary

- **Authorization:** non-staff actors are refused before any run is created (no
  anonymous discovery; no new identity system; no public endpoint; no UI).
- **RLS:** the write path is `service_role`, server-only (staff-only SELECT
  unchanged). Full RLS verification ships with the approved migration + DB adapter.
- **Security:** untrusted metadata is sanitized (M7.1/M7.2), the host/HTTPS/size
  policy is enforced by the providers, errors are redacted, and no raw payload or
  secret enters the run result.
- **AI boundary:** the orchestrator imports no `@wise-evidence/ai`; discovery runs
  with AI absent.
- **Canonical boundary:** the store ports expose only run/candidate writes; there
  is no code path to canonical creation or publication.
