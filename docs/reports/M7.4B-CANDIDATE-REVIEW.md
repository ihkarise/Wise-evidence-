# WiseEvidence M7.4B Checkpoint

_Discovery candidate review workflow — human accept/reject/link/correct/refetch/defer._
_See `docs/30` §11, `ADR-020`. Offline PGlite verification; live Supabase PENDING._

## Completed

The human review workflow over automated-discovery `import_candidate` rows. Staff
can list and inspect candidates and take one of six structured actions —
**Accept, Reject, Link duplicate, Correct, Refetch, Defer**. Accept starts the
**existing** manual research lifecycle (a `DRAFT` via `createDraftFromMetadata`)
and stops there; it never publishes, classifies, calls AI, or deletes anything.
Traceability source → run → candidate → study is preserved with the existing
schema, so **no migration** was added (migrations remain `0001`→`0013`).

## Candidate List

`GET /admin/imports` → `listCandidates(db, actor)`. Staff-only, newest first,
optional state filter (Review required / Possible duplicates / Imported /
Rejected). Shows only discovery candidates (`source_key is not null`) with a safe
title/DOI/dedup/state summary — no classification or efficacy field exists to leak.

## Candidate Detail

`GET /admin/imports/[id]` → `getCandidateDetail(db, actor, id)`. Full untrusted
(auto-escaped) metadata, provenance (source, source key, stable id, provider
version, raw hash, discovery run id), dedup verdict/reason, any linked existing
study (resolved by DOI), proposed corrections, and the action controls (only while
the candidate is reviewable).

## Authentication

Reuses Supabase Auth + `apps/web/src/middleware.ts`: `/admin` and `/api/admin` are
gated to a signed-in staff actor resolved server-side (`auth.uid()` → `app_user` →
role). No new auth system.

## Authorization

Every service function calls `requireStaff(actor)` (defense in depth over RLS).
The actor comes from the server session, never the client. RLS is unchanged and
authoritative: `import_candidate` keeps staff-only SELECT and full anon denial;
writes run the privileged (`service_role`) path exactly like the M3 editor. Tests
cover reviewer + admin allowed, PUBLIC forbidden, anon fully denied (select /
update / delete all rejected), and a signed-in reviewer reading through RLS.

## Accept

`acceptCandidate` → `createDraftFromMetadata` (DOI/title/metadata from the
candidate's own normalized payload; `sourceName` = the discovery source so the
draft's `research_source` is shared with the run). Result: a `lifecycle=IMPORTED`,
`publication_state=DRAFT` study; the candidate becomes `IMPORTED`; an append-only
`candidate_accepted` audit row records `{studyId, sourceKey, sourceStableId}`. If a
study already owns the DOI, no second study is created — the candidate is linked as
a `DUPLICATE_CANDIDATE`. Accept is refused for a candidate with no valid DOI and
for a non-reviewable state.

## Reject

`rejectCandidate` → terminal `FAILED` with `error_detail = reason`; row retained
(never deleted); audit `candidate_rejected`. A rejected candidate cannot then be
accepted (invalid-state).

## Link Duplicate

`linkCandidateDuplicate` → validates the target study **server-side**, sets
`duplicate_of_study_id`, state `DUPLICATE_CANDIDATE` (still reviewable), audit
`candidate_linked_duplicate`. Unknown study → not-found; malformed id →
invalid-input.

## Correct

`correctCandidate` → inserts an `OPEN` row in the existing `correction` table
(`target_type='import_candidate'`), audit `candidate_correction_proposed`. The
candidate's `normalized_payload` is **not** mutated (discovery provenance
preserved); the correction is itself reviewable and surfaced on the detail page.

## Refetch

`requestCandidateRefetch` → audit `candidate_refetch_requested` only. **No network
I/O and no arbitrary URL fetch** — the actual bounded, host-pinned re-fetch is the
discovery orchestrator's job (M7.2/M7.3). State unchanged.

## Defer

`deferCandidate` → audit `candidate_deferred` with an optional note; the candidate
stays in the queue (`REVIEW_REQUIRED`).

## Provenance

Preserved end-to-end without a new column: `import_job.source_id` → discovery
`research_source`; `import_candidate` carries `import_job_id` + `source_key` +
`source_stable_id`; on accept the created `publication.source_id` is that same
source and `research_identifier.value_canonical` equals the candidate's DOI; the
`candidate_accepted` audit entry links candidate → study. A test asserts the shared
source and the DOI↔identifier match.

## Audit

Every mutation writes an append-only `audit_log` row (`import_candidate` entity)
via the existing audit table — no new audit system. Actions:
`candidate_accepted`, `candidate_accept_existing`, `candidate_rejected`,
`candidate_linked_duplicate`, `candidate_correction_proposed`,
`candidate_refetch_requested`, `candidate_deferred`.

## Idempotency

Re-accepting an already-`IMPORTED` candidate is refused (`invalid-state`) — no
second study is created. DOI dedup in `createDraftFromMetadata` prevents a
duplicate canonical record when a study already owns the DOI. The M7.4A DB-enforced
candidate identity (`0013` partial unique index) is unchanged.

## RLS

Unchanged and authoritative. `import_candidate` / `import_job`: staff-only SELECT,
anon fully denied; canonical writes governed as in M3. No policy was added,
weakened, or removed. No new migration.

## Security

Client input is never trusted for identity, role, lifecycle/publication state,
study id, or classification. Ids are validated (UUID); the target study for a
duplicate link is verified to exist. Untrusted source metadata is auto-escaped by
Astro (never `set:html`). `ServiceError` messages are safe and non-secret-leaking.

## AI Boundary

No AI is invoked anywhere in the review path. A test asserts `ai_job` / `ai_result`
stay empty after accept.

## Classification Boundary

Accept creates **no** `classification` row and sets no outcome / quality /
confidence / evidence level. A test asserts zero classifications after accept.
Classification remains the separate, human-controlled M3/M6 step.

## Publication Boundary

Accept produces `publication_state = DRAFT` only. Nothing in M7.4B transitions to
`PENDING_REVIEW` or `PUBLISHED`. Tests assert no `PUBLISHED` study is produced by
the review path.

## Risks

- Accept requires a valid DOI (Crossref candidates always have one); DOI-less
  candidates must be corrected or link-routed first — surfaced as a clear
  `invalid-input`.
- Rejected candidates use the `FAILED` state (the enum has no dedicated `REJECTED`
  value); the audit action `candidate_rejected` and `error_detail` disambiguate.
  A future enum value would need a migration and is intentionally deferred.
- Accept runs `createDraftFromMetadata` (atomic) then a candidate-state update +
  audit as sequential statements (matching the M3 pattern), not one outer
  transaction — a narrow non-atomic window, acceptable and consistent with M3.

## Scope Check

Only the human candidate-review workflow was built. No scheduler, queue, Hermes,
scraping, new provider, publication, classification, effectiveness scoring, AI,
candidate deletion, or new table. Reused: Supabase Auth, middleware, service layer,
`audit_log`, `createDraftFromMetadata`, the `correction` table, existing RLS, and
existing provenance structures.
