## 4. Provider

The benchmark uses the **existing** `OpenAICompatibleProvider`
(`packages/ai/src/providers/openai.ts`) through the existing orchestrator
(`packages/ai/src/orchestrator.ts`). No new provider abstraction and no second AI
architecture were created (master prompt §8, §11).

Provider posture (unchanged from M6):
- generic OpenAI-compatible `POST {baseUrl}/chat/completions`, `temperature: 0`,
  `response_format: { type: "json_object" }`;
- **`fetch` is injected** → fully offline-testable, no live call in CI;
- API key lives only in the `Authorization: Bearer …` header, constructed
  server-side, never logged, never persisted, never returned in an error;
- `AbortController` timeout-bounded and response-size-bounded (256 KiB default);
- model output is **untrusted** and validated by the caller before persistence.

OpenRouter is one compatible endpoint, supplied only through server-side
`AI_BASE_URL` / `AI_API_KEY`; it is **not** hard-coded into `packages/ai`.

## 7. Benchmark Methodology

The harness (`packages/benchmark`) holds **MODEL as the only experimental
variable** (master prompt §11). Held constant across every model: the DEMO study,
the task set, the exact per-task input, the prompt version and content, the system
instruction, the output schema and validation, `temperature: 0`, the retry policy,
and the request structure — all inherited from the shared `@wise-evidence/ai`
orchestrator so no model gets a different code path.

Two workloads (master prompt §12):
- **FULL** — the six approved tasks: `research-summary`, `outcome-classification`,
  `evidence-quality`, `criticism-extraction`, `metadata-extraction`,
  `duplicate-detection`.
- **ESSENTIAL** — the four reviewer-critical tasks: `research-summary`,
  `outcome-classification`, `evidence-quality`, `duplicate-detection`. The
  repository did not previously define ESSENTIAL; this follows the master-prompt
  definition verbatim (documented, master prompt §12).

Call discipline (master prompt §29): each model runs FULL **once**; ESSENTIAL is
**derived** from the FULL measurements, not re-called — the fewest calls that
answer the benchmark.

## 23. Cache Verification

**Verified offline.** Cache identity = `(study, operation, input_hash, model,
prompt_version)`. The harness `cacheKeyParts()`/`cacheKeyString()` and its tests
prove isolation: changing the **model**, the **prompt version**, or the **input**
each yields a different identity, and an identical request yields the same identity.
At the database layer (M6, `packages/database/test/ai.test.ts`) a cache **hit makes
no second provider call**, and a differing model/prompt/input is a cache **miss** —
so a stale suggestion can never masquerade as current. Inference measurements are
taken on cache misses, so they are not distorted by cache hits.

## 27. Cache Economics

Cache hits occur on a repeated identical `(study, operation, input_hash, model,
prompt_version)` and make **no** provider call — so re-opening an editor, re-running
an unchanged task, or reloading a study costs nothing. The cache is invalidated
(correctly) by a **new prompt version**, a **model change**, or an **input change**,
because each changes the identity — a safety property, not a loss: a suggestion from
a superseded prompt or model must not silently stand in for the current one. Net AI
spend therefore scales with _distinct_ (study × task × model × prompt-version ×
input) tuples, not with page views. A precise hit-rate saving is **PENDING** live
usage.

## 28. Single-Model vs Mixed-Model Analysis

**Recommendation deferred to the live gate**, but the decision framework is fixed:

- **Option A — one model for all six tasks.** Simplest: one config, one cost line,
  one prompt-compatibility surface, one failure mode. Lowest operational risk.
- **Option B — cheap model for ESSENTIAL + a stronger model for the harder tasks**
  (e.g. criticism-extraction). Justified only if the live rubric shows the cheap
  model's edit burden on those tasks is materially worse.
- **Option C — a different model per task.** Highest complexity and maintenance
  (six configs, six cost lines, six prompt-compat checks); adopt only for a large,
  measured benefit.

Prior (cost-first, ADR-010): **prefer Option A with the cheapest candidate that
clears the reliability/grounding bar**, and only move to B if the live data forces
it. No mixed architecture "because it looks impressive" (master prompt §25, §39).
