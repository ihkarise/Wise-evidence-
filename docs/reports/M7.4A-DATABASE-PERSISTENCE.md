## Migration 0013

Additive only, confirming the M7.3 finding against the real schema:
`import_candidate` had no `source_key` / `source_stable_id` column and no unique
constraint. The migration adds those two nullable columns plus one PARTIAL unique
index. It touches no other table and adds no RLS policy, AI/canonical field, or
scheduler/queue infrastructure.

## Schema Change

```sql
alter table import_candidate
  add column source_key       text,
  add column source_stable_id text;

create unique index if not exists import_candidate_source_identity_uniq
  on import_candidate (source_key, source_stable_id)
  where source_key is not null and source_stable_id is not null;
```

## Idempotency

DB-enforced. `insertCandidate` uses `INSERT … ON CONFLICT (source_key,
source_stable_id) WHERE … DO NOTHING RETURNING id`; on conflict it reads and
returns the existing candidate. The **database constraint is the final
authority** (not an application-only SELECT-then-INSERT), and the existing
candidate is **preserved** — a re-discovery never overwrites its payload with a
newer one. Verified: a raw duplicate insert is rejected; two adapter inserts of
the same identity yield one row (`created:true` then `created:false`, same id,
original payload kept); a full re-run persists zero new candidates.

## NULL Identifier Policy

The unique index is **partial** (`WHERE source_key IS NOT NULL AND source_stable_id
IS NOT NULL`), so candidates without a discovery identity — manual entries and the
DEMO fixtures — never participate and never collide. Verified: two NULL-identity
candidates coexist. The orchestrator only persists items that have a stable source
id, so discovery-created rows always carry both columns.

## Database Adapter

`DatabaseDiscoveryStore` (implements `DiscoveryRunStore` + `CandidateStore`) and
`DatabaseStudyIndex` (implements the read-only `KnownStudyIndex`). Persistence
only: no provider, pagination, dedup algorithm, AI, or UI logic. The orchestrator
stays provider-neutral and unchanged. `research_source` is get-or-created by name
per source key (no per-run duplication); `research_source` has no natural unique
key, so this is an application-level find-or-create (documented limitation — not
the racy candidate path).

## Import Job Persistence

`createRun` inserts an `import_job` (`RUNNING`, source_id, trigger, started_at);
`finalizeRun` updates it to `COMPLETED` / `FAILED` with the counters (JSONB
`counts`), `ended_at`, and a safe `error_detail` summary. Only existing columns
are used — no `import_job` schema change. Verified: RUNNING→COMPLETED with correct
counters; FAILED recorded for an unconfigured-provider run.

## Candidate Persistence

Each candidate row carries `import_job_id`, `source_key`, `source_stable_id`, the
minimised `normalized_payload` (JSONB, no full text), `dedup_decision` (JSON text),
`duplicate_of_study_id` (set only for a valid study match), and a reviewable
`state` (`REVIEW_REQUIRED` / `DUPLICATE_CANDIDATE`). No `PUBLISHED` / `ACCEPTED` /
`CLASSIFIED` state is ever produced by discovery.

## Provenance

The normalized payload retains source key, stable id, source URL, DOI,
identifiers, discovery/fetch timestamps, connector version, and the raw-payload
SHA-256 hash. No full papers or raw HTTP responses are stored; no headers,
credentials, or secrets are persisted (data minimisation).

## Duplicate Handling

Candidate-level idempotency `(source_key, source_stable_id)` and research-level
deduplication are kept distinct. `DatabaseStudyIndex` reads
`research_identifier` / `research_study` / `publication` to grade a candidate
(DOI → persistent id → normalized title+year → title) → DEFINITE / PROBABLE /
POSSIBLE / NEW. A DEFINITE match records `duplicate_of_study_id`; the new candidate
is still persisted and the existing study is untouched (`DUPLICATE ≠ DELETE`).
Verified end-to-end against a seeded study.

## RLS

Unchanged by the migration. `import_candidate` / `import_job` keep staff-only
SELECT and no INSERT/UPDATE policy; writes are the `service_role` server path
(bypasses RLS). Verified on PGlite: **anon cannot SELECT/INSERT/UPDATE/DELETE**
`import_candidate` (all reject); `service_role` reads the persisted rows. **PGlite
verified; live Supabase verification pending.**

## Authorization

Discovery persistence is staff-controlled: the orchestrator refuses non-staff
actors, and `DatabaseDiscoveryStore` additionally calls `requireStaff` at
construction (defense in depth). No public endpoint, no browser exposure of
`service_role`, no second auth system. Verified: constructing the adapter with a
`PUBLIC` actor throws.

## Security

No secrets, no credential persistence, no arbitrary URL fetch, no public discovery
trigger, no RLS weakening, no canonical writes, no AI. `service_role` is used only
inside the server-side test/harness path and is never logged or returned. Secret
scan and `git diff --check` clean.

## Risks

- Live Supabase application of `0013` and live RLS verification are pending
  (PGlite-verified only).
- `research_source` has no natural unique key, so the run's source row is
  find-or-created at the application level; a concurrent first-ever run for a new
  source could create two source rows (benign, not the candidate path). Fixing it
  would need a separate, unrelated migration — out of this milestone's approved
  scope, so it was not done.
- True multi-connection concurrency is not reproducible in single-connection
  PGlite; the DB unique constraint and `ON CONFLICT` behaviour are verified, which
  is the mechanism that guarantees production concurrency safety.
